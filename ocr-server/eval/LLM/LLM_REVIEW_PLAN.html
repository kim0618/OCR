실물 확인 전량은 부류별 파일에서

이 문서엔 숫자만 둔다. 실물은 부류별 파일에서 전량 본다 - 카드 한 장이 문서 하나이고 원본 → Base 전처리 후(우리가 OCR 에 먹인 것) → 모델 전처리 후(VLM 이 실제로 본 것) 이미지 세 장을 화면 폭에 꽉 차게 놓는다. 양쪽이 원본에 무슨 짓을 했는지가 같은 자리에서 갈린다. 표본 몇 개만 보면 부류가 한 덩어리인지 흩어진 사고인지 알 수 없고, 회귀가 12건이냐 300건이냐로 채택 판단이 뒤집힌다.
부류문서전량 보기무엇을 판정하나
모델이 살린 것 Base 붕괴 → 모델 정상? LLM_CASES_REVIVED.html 원본은 똑바른데 전처리 후가 돌아가 있으면, 원인은 모델 실력이 아니라 우리 전처리다
모델이 망친 것 Base 정상 → 모델 붕괴? LLM_CASES_REGRESSED.html 채택하면 새로 잃는 것이다. 한 부류로 묶이는지가 채택 여부를 가른다
둘 다 틀린 것 양쪽 붕괴? LLM_CASES_BOTHFAIL.html 전처리로도 모델로도 안 되는 잔여 - 다음 라운드의 재료다
위 두 표의 소생 · 회귀 · 둘 다 실패 칸도 같은 파일로 이어진다 - 숫자를 누르면 그 문서군의 실물로 바로 간다. 요약 하나 + 상세 여러 개는 DEMO_SUMMARY / DEMO_REPORT_* 와 같은 구조다.
재료 - 전처리 후 이미지는 eval 을 돌리면 나온다. 서버 응답의 processed_image(OCR 이 실제로 먹은 이미지)를 run_batch.py 가 runs/<ts>/processed/<src>.jpg 로 저장한다 - AWS run 에 있으니 회수해서 쓴다(로컬 재현 금지). 원본은 로컬에 있다(samples/ 의 imagePath · data/invoice_war/images_replay/). 변환 파라미터도 samples/ 에 남는다(orientation.angle · koreanReverify.pickedRot · deskew.rawAngle · document 워프) - 카드 캡션에 무슨 처리를 했는지 적는 데 쓴다.
전수 9,001 은 이미지 없이 분류한다 - 오회전은 full_text 가 페이지 맨 아래 문구부터 시작하는 지문이 있다 (실물 판독으로 확인 · 27809). 이 지문으로 전수를 가르고, 이미지는 그 분류가 맞는지 검증하는 데만 쓴다.
수록 범위 - 소생 · 양쪽 붕괴는 오회전(회전 적용 · 붕괴) 135장만 싣는다. 전처리 축의 답은 그 한 행이고 나머지 문서군은 위 계량표의 숫자로 충분하다. 회귀만 전 문서군을 싣는다 - 모델이 정상 문서를 망치는 것이 채택을 막는 가장 큰 리스크인데 오회전만 실으면 그게 안 보인다.
세 파일은 llm_cases_report.py 가 찍는다 - 손으로 쓰지 않는다. 시안은 --sample 로 만들어 뒀다(값은 가짜 · 이미지는 실물 · “Base 전처리 후”는 회전을 걸어 흉내낸 것). 수록 문서군은 --groups 로 바꾼다.

보류 - 이번 검토는 전처리와 파서만 진행하기로 했다. 아래 설계는 그대로 두고 실행하지 않는다. 선행 조건은 전처리·파서 단계에서 승자 모델이 정해지는 것이다.
wf80 이 판정받은 그 무더기에 500장 스크리닝 승자(선정 모델) 열을 얹는다. 타깃 지정 전(L0)과 후(L1)를 둘 다 재서, Paddle 쪽 “후”는 재학습(wf80), LLM 쪽 “후”는 LoRA 파인튜닝이다. 차이 열은 같은 조건끼리 짝지은 것이다 - L0 − base 는 손대지 않은 상태의 순수 대체력, L1 − wf80 은 타깃을 지정해 학습시킨 뒤의 대체력. 가로로 읽으면 base → wf80 과 L0 → L1, 즉 양쪽의 소생 폭 자체를 비교할 수 있다.

운영에서 타깃을 어떻게 아는가는 이 표 밖이다 - Paddle 은 가중치에 들어있고 LLM 은 매번 골라줘야 하는데, 그 선택 문제가 ④ 마스터매칭층이다. 이 검토의 범위는 “타깃 소수를 지정했을 때의 소생력과 부작용”까지다.
