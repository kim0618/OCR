2026-06-22 합의. 거래명세서 OCR의 "학습 룰 vs 파인튜닝" 개념 정리 + 따라잡기 전략 + 인프라 구축.

**2층 구조 (모든 판단의 출발)**: ① 인식(recognition, 이미지→글자, GPU/모델, "못 읽음") / ② 파싱(parser, 글자→필드, CPU/룰, "읽었는데 못 담음"). `parser_drop_classify`가 결함을 ①/②로 자동 분류.

**학습 룰 = 현재 우리 루프 ≠ 모델 학습**: 고정 PP-OCR 위에서 파서(룰)만 측정·개선하는 반복. 셀 손실 98%가 파서(값은 OCR에 이미 있음)라 룰로 회수 가능. 로컬 replay=스냅샷 위 재-OCR 없이 파서 재실행. [[project_ocr_snapshot_replay]] [[project_preprocess_complete_24base]]

**파인튜닝 = 별개의 모델 학습(미래)**: PP-OCR rec(LLM 아님, 작은 이미지→글자 인식기, 이미 수백만장 사전학습됨)을 가져와 우리 (크롭,정답)로 추가학습. 역전파+경사하강으로 가중치 미세조정→그 글꼴 시각특징 익혀 새 크롭도 읽음. 필요: GPU(AWS有)+사전가중치+**라벨된 크롭(없음=병목)**+dict+config+export. 우리 루프와 eval 측정기만 공유. dict=charset 파일(없는 글자는 출력 불가; 확장하려면 dict추가+샘플학습 둘다).

**순서(싼것→비싼것, 각 단계 측정 게이트)**: 1.룰 개선 → 2.마스터 매칭 복원(품목명/공급자/공급받는자) → 3.못읽는문자(모델교체·전처리 먼저, 반복되는 잔여만 파인튜닝). 파인튜닝은 항상 마지막. 파인튜닝 데이터는 못읽은것만 X → 정상샘플 섞어야(catastrophic forgetting 방지).

**따라잡기 전략(경쟁사=구글 API=인식엔진)**: 구글을 모델로 이기려 말고 **데이터 플라이휠**. 경쟁사 사람-보정 테이블 확보→ GT(점수판)+마스터사전(즉시)+파인튜닝 코퍼스(크롭정렬·인식오류필터 후). 목표 도메인에선 "좋은 모델"아닌 "도메인 파서+보정데이터"로 따라잡기 현실적. 범용 OCR로 구글 전체 이기긴 비현실적이고 그럴 필요도 없음. 격차는 수천장 측정으로 숫자화됨.

**이번 구축 인프라(checker-safe, 서버 무수정)**: 자세한 파일/위치/검증은 [[project_finetune_ledger_infra]].
