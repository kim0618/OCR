2026-07-27. "base 모델 대비 한글/숫자가 얼마나 +되나"를 정직하게 재는 고정 벤치 구축. 회사 목적=업체가 정답+이미지 N장 주면 못읽던 글자 읽게 되나 → **UNSEEN 델타가 그 답**. [[project_finetune_fields_round]]의 same-crop 방법론을 고정셋으로 제도화.

## ★핵심 설계 = 리포트 1개, 탭 2개 (SEEN / UNSEEN)
- **UNSEEN** = 9,001 held-out 문서의 **실패 크롭**. "처음 보는 송장의 안 읽히던 셀을 FT가 얼마나 읽나" = **회사 답**. **영구 고정**(한 번 얼리면 라운드 불변 → split 재생성 착시 차단).
- **SEEN** = 그 run이 **실제 학습에 쓴 실패 크롭**(UNSEEN 컬럼분포 매칭 샘플). "외운 것 재현 상한". **run 종속 = 라운드마다 재빌드**(train.txt 바뀌면 바뀜).
- **SEEN↔UNSEEN 간격 = 순수 일반화**(간격 크면 암기, 작으면 진짜 실력). 4차에서 한글 동반붕괴=일반화 실패 신호였음.
- 양쪽 다 **실패-크롭 구성**이라 구성편향 상쇄 → 판정은 절대% 아니라 **base→FT 델타**(같은 크롭에서 base·FT 둘 다 채점하니 델타 공정).

## ★왜 "실패 크롭"만인가 (데이터 제약, AWS 실측)
- 9,001 크롭 = ledger.jsonl에 **343,567개 전부 recognition 실패**(src·컬럼 있음, 식별가능). **현 train/val/test에 유출 0**(전량 미사용 확인).
- **정답/balance 크롭(crops_correct 340만)은 src 메타 없음** → 어느 게 9,001인지 못 가림 + **processed 이미지 삭제**로 새로 못 자름. 따라서 "9,001 전 셀(쉬운 것 포함)"은 불가, **실패 셀만** 깨끗. (오히려 회사질문="안 읽히는 셀"에 정확히 맞음.)
